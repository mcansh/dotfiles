<skill_overview>
Runs the full SonarQube analysis locally using dotnet-sonarscanner: begin → build → test (with coverage) → end. Results are uploaded to the SonarQube server and then queried via MCP tools for a consolidated report. This lets you get SonarQube feedback before pushing code.
</skill_overview>

<rigidity_level>
MEDIUM FREEDOM — The four-phase scanner workflow (begin, build, test, end) is rigid. Project key detection and result reporting are flexible.
</rigidity_level>

<when_to_use>
- User says "local scan", "sonar scan", "scan locally", "run sonarscanner"
- User wants SonarQube results before pushing
- Project doesn't have CI-based SonarQube scanning yet
- User wants to verify quality gate will pass before a PR
</when_to_use>

<the_process>

## 1. Detect Project Context

Determine the solution file, project key, and branch:

```bash
# Find solution file
ls *.sln

# Get current branch
git rev-parse --abbrev-ref HEAD
```

**Project key detection** — try these in order:
1. Check for `sonar-project.properties` file → read `sonar.projectKey`
2. Check the repo directory name (often matches the SonarQube key)
3. Search SonarQube via `mcp__sonarqube__components` with the repo name
4. If not found, use the repo directory name as the key (will create a new project on first scan)

Known project key mappings:

| Repo | SonarQube Key |
|---|---|
| brand360-gateway | `cell-biz-marketing-gateway` |
| brand360-contact-validate | `cell-biz-contact-info-validate` |
| lead-ingestion | `cell-biz-lead-profile` |
| loa-text-messaging | `cell-text-messaging` |
| cell-communications-emailer | `cell-communications-emailer` |

## 2. Verify Prerequisites

```bash
# Check sonarscanner is installed
DOTNET_ROOT=/home/ycollins/.dotnet /home/ycollins/.dotnet/dotnet tool list -g | grep sonarscanner

# Check SONARQUBE_TOKEN is set
echo "${SONARQUBE_TOKEN:+SET}"

# Check all test projects have coverlet.collector for coverage
find . -path "*/test*/*.csproj" -exec grep -L "coverlet.collector" {} \;
```

If sonarscanner is not installed:
```bash
DOTNET_ROOT=/home/ycollins/.dotnet /home/ycollins/.dotnet/dotnet tool install --global dotnet-sonarscanner
```

If any test project is missing `coverlet.collector`, add it:
```bash
DOTNET_ROOT=/home/ycollins/.dotnet /home/ycollins/.dotnet/dotnet add <test-project.csproj> package coverlet.collector
```

Without `coverlet.collector` in every test project, coverage data will be incomplete — SonarQube will report 0% for code only covered by tests in projects missing this dependency.

If SONARQUBE_TOKEN is not set, tell the user to run `/setup-quality-tools`.

## 3. Run the Scanner (Four Phases)

### Phase 1: Begin

```bash
DOTNET_ROOT=/home/ycollins/.dotnet /home/ycollins/.dotnet/dotnet sonarscanner begin \
  /k:"<project-key>" \
  /d:sonar.host.url="https://sonarqube.uwm.com" \
  /d:sonar.token="$SONARQUBE_TOKEN" \
  /d:sonar.branch.name="<current-branch>" \
  /d:sonar.cs.opencover.reportsPaths="**/coverage.opencover.xml"
```

The `sonar.cs.opencover.reportsPaths` glob tells the scanner where to find coverage reports generated by coverlet in Phase 3.

### Phase 2: Build

```bash
DOTNET_ROOT=/home/ycollins/.dotnet /home/ycollins/.dotnet/dotnet build <solution-file> --no-incremental
```

The `--no-incremental` flag ensures all source files are compiled and analyzed. Without it, unchanged files may be skipped by the Roslyn analyzers.

### Phase 3: Test with Coverage

```bash
DOTNET_ROOT=/home/ycollins/.dotnet /home/ycollins/.dotnet/dotnet test <solution-file> \
  --no-build \
  --collect:"XPlat Code Coverage" \
  -- DataCollectionRunSettings.DataCollectors.DataCollector.Configuration.Format=opencover
```

This runs all tests and generates `coverage.opencover.xml` files in each test project's `TestResults/` directory. The `--no-build` flag reuses the instrumented build from Phase 2.

**Important:** Every test project must have `coverlet.collector` as a package reference. Without it, that project's tests will run but produce no coverage data.

Some tests may fail in local environments (e.g., tests requiring network shares, specific infrastructure). This is expected — the coverage data from passing tests is still valid and will be uploaded.

### Phase 4: End

```bash
DOTNET_ROOT=/home/ycollins/.dotnet /home/ycollins/.dotnet/dotnet sonarscanner end \
  /d:sonar.token="$SONARQUBE_TOKEN"
```

This uploads code analysis AND coverage data to the server. Wait for the "ANALYSIS SUCCESSFUL" message before querying results.

## 4. Query Results via MCP

After upload completes, query the SonarQube MCP tools — run these in parallel:

1. `mcp__sonarqube__quality_gate_status` — pass/fail status
2. `mcp__sonarqube__measures_component` — metrics:
   - `bugs`, `vulnerabilities`, `code_smells`, `coverage`, `duplicated_lines_density`
   - `new_bugs`, `new_vulnerabilities`, `new_code_smells`, `new_coverage`, `new_duplicated_lines_density`
3. `mcp__sonarqube__issues` — open issues filtered to `OPEN`, `CONFIRMED`, `REOPENED`

If issues are found:
- Read the flagged file and understand the issue
- Offer a fix
- After fixing, offer to re-run the local scan to verify

<critical_rules>
- ALWAYS use `DOTNET_ROOT=/home/ycollins/.dotnet /home/ycollins/.dotnet/dotnet` — the system dotnet at `/usr/bin/dotnet` only has .NET 10 and may not match the project's target framework
- ALWAYS use `--no-incremental` on the build to ensure full analysis
- ALWAYS run tests with `--collect:"XPlat Code Coverage"` between build and end — without this, SonarQube will report 0% coverage
- ALWAYS include `sonar.cs.opencover.reportsPaths` in the begin phase so the scanner knows where to find coverage reports
- ALWAYS verify every test project has `coverlet.collector` before running — missing this dependency is the #1 cause of incomplete coverage data
- NEVER expose or echo the SONARQUBE_TOKEN value — use `$SONARQUBE_TOKEN` variable reference
- ALWAYS wait for "ANALYSIS SUCCESSFUL" or "Post-processing succeeded" before querying MCP results — the server needs time to process the uploaded report
- If the scan creates a new project on SonarQube (first scan), note this to the user — they may need to configure the quality gate profile on the server
- Local coverage may be lower than CI coverage if some tests require infrastructure not available locally (network shares, specific services). This is expected — note the difference to the user
</critical_rules>
